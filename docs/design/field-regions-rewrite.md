# Design: field regions rewrite + region editor

**Status:** Part 1 (MW-Lib) implemented on `claude/exciting-bohr-efq7zb`, based on `develop-2027`. Parts 2 and 3 not started.
**Scope:** MW-Lib (new region library), a new team repo for the region editor (based on
[RegionBool](https://github.com/Arthur225/regionbool), MIT), and a later, off-season mainbot migration.
**App name:** Mariner (Mariner 9 was the first spacecraft to map Mars). In the editor the name is
one constant (`src/shared/brand.ts`).

## Why

Today mainbot keeps 14 hand-typed `PolygonRegion`s in `lib2026/FieldRegions.java`, and
`Robot.disabledPeriodic()` calls `FieldRegions.flipRegions()` whenever the alliance changes.
That causes four problems:

1. **`flipRegions()` toggles instead of setting a side.** Its javadoc says "does not keep track of
   Red/Blue". The regions are only right if the robot saw an even/odd number of alliance changes.
2. **`HOLD_REGIONS` is never flipped (bug).** The `ArrayList` holds the original objects, and
   `flipRegions()` reassigns the static fields to new objects. On red, `GameStatesSubsystem`'s
   hold-zone check uses blue's zones.
3. **Each flip builds new `PolygonRegion`s,** and each constructor makes another NetworkTables publisher.
4. **The regions are typed out by hand.** You can't see them until they show up in AdvantageScope.

## Goals

- Regions that never change, and that work out the alliance on every check. No flip call to remember.
- Shapes: rotated rectangles, circles, polygons/triangles, and unions with holes.
- Named groups (e.g. `HOLD_REGIONS`) generated by the editor, not kept by hand.
- Outlines published to NetworkTables once, and again only when the alliance changes.
- The editor draws regions and writes a **thin** generated Java file: data and constructors only.
  All the geometry lives in tested MW-Lib code.

## Non-goals

- Changing mainbot this season. The migration is off-season (see Phase 3).
- Generated "opponent" mirrors. OPP regions are still drawn separately in the editor.
- `willContain(pose, speeds, t)`. Nothing uses it, so it's dropped (it's easy to add back).

## Part 1: MW-Lib region library

New package `com.marswars.regions`. It replaces `com.marswars.geometry.Region`,
`PolygonRegion`, `CircularRegion` and the `AllianceFlipUtil.apply(Region…)` overloads, which are
deleted. It's a breaking change, so it ships in the **27.x** line (branch `develop-2027`), not in
26.x. mainbot pins 26.17.4 and keeps it until it migrates; moving mainbot to 27.x also brings in the
rest of 27.x's changes. `AllianceFlipUtil` itself stays, for poses and translations.

### Types

```java
// Field size, origin and symmetry. Written into the generated file by the editor, per season,
// so no AllianceFlipUtil.configureFieldGeometry() call is needed for regions.
public record FieldGeometry(double lengthMeters, double widthMeters,
                            Symmetry symmetry, Origin origin) {}
public enum Symmetry { ROTATIONAL, MIRRORED }   // 2026 REBUILT: ROTATIONAL
public enum Origin   { BLUE_CORNER, CENTER }

// Shapes. Immutable; contains() is allocation-free.
public sealed interface Shape permits Shape.Rect, Shape.Circle, Shape.Polygon {
    static Shape rect(double cx, double cy, double width, double height, double rotationDeg);
    static Shape rect(double cx, double cy, double width, double height, double cos, double sin);
    static Shape box(double x1, double y1, double x2, double y2);   // axis-aligned, two corners
    static Shape circle(double cx, double cy, double radius);
    static Shape polygon(double[] xs, double[] ys);      // triangles are 3-point polygons
    static Shape polygon(Translation2d... points);       // a repeated closing point is dropped
    boolean contains(double x, double y);
    Translation2d[] outline();                           // closed loop
}

public enum AllianceMode { FLIPS, FIXED }

public final class FieldRegion {
    public static Builder builder(String name, FieldGeometry field);
    // Builder: .flips() / .fixed(), .add(Shape...), .subtract(Shape...), .build()

    public boolean contains(Pose2d pose);
    public boolean contains(Translation2d point);
    public boolean contains(double x, double y);
    public boolean containsAsDrawn(double x, double y);   // ignores the alliance
    public String name();
    public AllianceMode allianceMode();
    public List<Translation2d[]> outlines();    // for the current alliance; allocates
}

public final class RegionGroup {                // fixes the HOLD_REGIONS problem by design
    public static RegionGroup of(String name, FieldRegion... regions);
    public boolean contains(Pose2d pose);       // in any member
    public List<FieldRegion> regions();
}
```

### "Inside" rules (same as the editor, so what you draw is what the robot checks)

- A point is in a region if it's in at least one added shape and in no subtracted shape.
- Edges count as **inside**, within 1e-9 m. So a point exactly on a hole's edge is outside the region.
  (Today's `CircularRegion` uses a strict `<`. The difference is nanometers.)
- Polygons use the even-odd rule.

### Alliance handling

Shapes are always stored in **blue-corner** coordinates, the same as the editor's file.
`FieldGeometry.origin` is the system the robot's poses are in. `contains` converts the queried point
to blue-corner coordinates first (for `CENTER`: `(L/2 - x, W/2 - y)`), then, for a `FLIPS` region on
red, flips the **point**, not the shapes:

| Symmetry | Flip (blue-corner coordinates) |
|---|---|
| `ROTATIONAL` | `(L - x, W - y)` |
| `MIRRORED` | `(L - x, y)` |

This is exactly the editor's arithmetic, in the same order, so the editor and the robot agree on
every point, even ones 1e-9 m from an edge. An earlier draft stored shapes in the robot's system
instead; Mariner's cross-check test found it rounded differently at the edges. Outlines are
published in the robot's system.

The alliance comes from a small `AllianceState` helper. It reads `DriverStation.getAlliance()` at most
once every 20 ms and caches the result. An unknown alliance counts as blue. Tests can force
the alliance with `AllianceState.overrideForTesting(...)`. Nothing is mutated or rebuilt when the
alliance changes, so references in lists and groups never go stale.

### Publishing outlines

`RegionPublisher.register(Collection<FieldRegion>)` creates one `StructArrayPublisher<Translation2d>`
per region outline, and publishes once. The first outline goes to `Regions/<name>`, the same topic as
today, so the existing AdvantageScope layouts keep working. Extra shapes and holes go to
`Regions/<name>/1`, `/2` and so on. `SubsystemManager`'s periodic loop
(which already calls `MwLog.periodic()`) calls `RegionPublisher.periodic()`. That republishes only when
`AllianceState` reports a change, so steady state costs one boolean compare per loop.
AdvantageScope shows the topics live, and AdvantageKit's NT logging records them. MW-Lib gains no
AdvantageKit dependency.

### Tests (JUnit, in MW-Lib)

- Each shape: inside, outside, on the edge, on a vertex, rotated rectangles at 0/45/90°.
- Unions and holes, including a point on a hole's edge.
- Flipping: both symmetries × both origins × red/blue/unknown.
- No stale references: a group built before an alliance change gives the right answer after it.
- Publisher: publishes once, republishes on change, never on a steady loop.
- Done: 28 tests in `src/test/java/com/marswars/regions/`.
- Still to do in Part 2: a cross-check using the same point fixtures as the editor's geometry tests
  (exported as JSON), so the editor and MW-Lib can never disagree.

## Part 2: The region editor (new repo)

- **Repo:** [`FRC-Team-4143/mariner`](https://github.com/FRC-Team-4143/mariner). This is a plain
  repo, not a GitHub fork, so pull requests stay in-house. It keeps RegionBool's full history up to
  upstream commit `46411fc869304857d9e3d85caa50e6166a0b4dd1`, with our changes on top. Because the
  history is shared, upstream fixes can still be merged or cherry-picked from an `upstream` remote.
  The MIT `LICENSE` and copyright are kept.
- **Branding:** colors and logo only. Swap upstream's navy/blue for the MARS/WARS brand red
  `#d5000e` and the dark/light neutrals from `marswars-apps/design` (copied in, not linked). The
  upstream three-panel layout stays. The logo is a **placeholder** red mark until a real logo file
  is provided. The 1156 logo is removed (it isn't covered by MIT).
- **Credit:** About box and README: "Based on RegionBool by Arthur Rodrigues Andrade and
  UnderControl 1156", plus the MIT notice.
- **Fields:** keep all bundled fields from 2022 to 2026.
- **Coordinates:** keep both blue-corner and field-center origins.
- **Kept from upstream:** diff before write, refusing to overwrite files it didn't generate,
  JSON regions file in the robot project, and the 2026 and 2027-alpha import profiles.

### Changes to the editor

1. **New code generator.** It writes MW-Lib types instead of self-contained math. The old standalone
   generator is removed.
2. **Output path and package are configurable per project** (`output.packageName`, `output.className`,
   `output.path` in the regions file). A new project defaults to `frc.robot.lib2026.FieldRegions`.
3. **Region groups.** A new `groups[]` in the regions file (name and member region ids), a small
   Groups panel in the editor, and one `RegionGroup` constant per group in the generated file.
4. **Adopting a hand-written file.** The first export onto an existing file the editor didn't
   generate shows the full diff and needs an explicit "Replace hand-written file" confirmation.
   After that, the normal hand-edit protection applies.
5. **Field symmetry and origin** go into the generated `FieldGeometry`, taken from the selected field
   and the project's origin setting.
6. **Renaming** the folder (`.regionbool/` → `.mariner/`), file header, app ID and installer names all
   come from the single name constant.
7. **Region descriptions.** Each region (and group) gets an optional description in the editor. It
   becomes the Javadoc on the generated constant, so IntelliSense in VS Code shows it when you hover
   over or autocomplete `FieldRegions.HOLD_ZONE`. The same text goes into the generated README.
8. **Region docs: images and a README, written on every export.** The editor already draws the
   field and regions, so it renders them to PNGs from the same canvas:
   - `docs/regions/all.png`: the field with every region, labeled.
   - `docs/regions/<REGION>.png`: the field with only that region, plus one per group.
   - `docs/regions/README.md`: generated. A title, the field and symmetry, the combined image, then a
     section per region and group with its image, description, `FLIPS`/`FIXED`, and the Java name to
     use. It carries a "GENERATED by Mariner" header and gets the same hand-edit protection as the
     Java file.

   The images are drawn as the blue alliance sees them, with a note saying flipping regions are mirrored on red. They go
   into the same export diff dialog (listed as changed or unchanged; images aren't diffed line by
   line). Regenerating the PNGs from the same input must give identical bytes, so git only sees a
   change when a region really moved.
9. **Releases:** keep upstream's release workflow for Windows, macOS and Linux installers (unsigned,
   as upstream).

### Generated file (example)

```java
// GENERATED by Mariner. Do not edit.
// Source: .mariner/regions.json

package frc.robot.lib2026;

import com.marswars.regions.*;
import java.util.List;

/** Field regions drawn in Mariner. Field coordinates in meters, origin at the blue corner. */
public final class FieldRegions {
    public static final FieldGeometry FIELD =
            new FieldGeometry(16.541, 8.069, Symmetry.ROTATIONAL, Origin.BLUE_CORNER);

    /**
     * Our side of the field, from the alliance wall to the starting line. Shooting at the hub is
     * allowed here.
     *
     * <p>Flips with the alliance. See docs/regions/README.md#alliance_zone.
     */
    public static final FieldRegion ALLIANCE_ZONE =
            FieldRegion.builder("ALLIANCE_ZONE", FIELD).flips()
                    .add(Shape.rect(1.9815, 4.021, 3.963, 8.042, 0.0))
                    .build();

    public static final FieldRegion HUB_REGION =
            FieldRegion.builder("HUB_REGION", FIELD).flips()
                    .add(Shape.rect(4.626, 4.025, 1.19, 1.19, 0.0))
                    .build();
    // ...

    public static final RegionGroup HOLD_REGIONS =
            RegionGroup.of("HOLD_REGIONS", HOLD_ZONE, OPP_HOLD_ZONE, OPP_ALLIANCE_HOLD_ZONE);

    public static final List<FieldRegion> ALL = List.of(ALLIANCE_ZONE, HUB_REGION /* ... */);

    static {
        RegionPublisher.register(ALL);
    }

    private FieldRegions() {}
}
```

The constants keep mainbot's current names and `.contains(pose)` calls, so most call sites don't change.

## Part 3: mainbot migration (off-season)

1. Bump the MW-Lib vendordep to the new major version.
2. Draw the 14 regions and the `HOLD_REGIONS` group in the editor, and export over
   `lib2026/FieldRegions.java` (adopt step).
3. Delete the `FieldRegions.flipRegions()` call in `Robot.disabledPeriodic()`.
4. `GameStatesSubsystem`: replace the `HOLD_REGIONS` loop with `FieldRegions.HOLD_REGIONS.contains(pose)`.
5. Check in sim on both alliances, and confirm the outlines in AdvantageScope.

The current `.contains(pose)` call sites in `LocalizationSubsystem`, `SimulationSubsystem` and
`GameStatesSubsystem` stay as they are.

## Decisions

- **Region docs folder:** `docs/regions/` by default, and selectable per project in the editor.
- **Package:** `com.marswars.regions`.
- **2027:** Mariner's WPILib 2027 output waits until MW-Lib moves to WPILib 2027. Until then the
  generator only targets 2026 (`edu.wpi.first`). Upstream's 2027 import profile stays in the code.
- **Today's regions:** no import script. The 14 regions get redrawn in Mariner during the migration.
- **MW-Lib version:** the 27.x line.
